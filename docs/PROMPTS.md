# PROMPTS

下面是和 Codex 协作时可直接复用的中文提示词模板。

## 1. 做一个小任务

```text
你现在是我的 macOS 原生开发工程师。
请只完成一个明确的小任务：
[在这里写任务]

要求：
1. 修改代码前先告诉我准备改哪些文件
2. 每次只完成一个小任务
3. 不要删除文件
4. 不要大规模重构
5. 修改后总结：改了什么、为什么改、如何测试
```

## 2. 只调整 UI

```text
请只调整 UI，不要改数据结构和应用启动方式。

本次只做这个任务：
[在这里写 UI 任务]

重点：
- 不要改无关文件
- 先说明准备修改哪些文件
- 修改后告诉我如何验证视觉效果
```

## 3. 只修复报错

```text
请只修复当前报错，不做额外优化。

要求：
- 先解释报错原因
- 再给修复方案
- 不要顺手重构别的部分
- 修改后告诉我如何验证
```

## 4. 继续做 notch / island 视觉

```text
请继续优化 macOS notch-style island 视觉。

本次只做：
[在这里写任务，例如“只调整 compact 形状”]

要求：
- 不要改无关文件
- 先说明改哪些文件
- 修改后告诉我：
  - island 是否贴顶
  - 是否还是单层背景
  - compact 是否仍然是一行
```

## 5. 生成下一步任务

```text
请根据当前项目状态，帮我拆分接下来的开发任务。

要求：
- 只按小任务拆分
- 优先级从高到低
- 每个任务一句话
- 不要直接改代码
```

## 6. 写文档

```text
请只补充项目文档，不要改 Swift 代码。

本次需要新增或修改：
[README.md / docs/ARCHITECTURE.md / docs/DESIGN.md / docs/TASKS.md / docs/PROMPTS.md]

要求：
- 使用中文
- 结构清晰
- 内容和当前项目实现保持一致
```

## 协作规则建议

每次发任务时都尽量包含：

- 这次只做什么
- 不要做什么
- 可以改哪些文件
- 修改后需要怎么验证
- 如果改到复杂路径、窗口定位、多屏逻辑或 SwiftUI 结构，顺手补有价值的详细中文注释

## 通用开发规则

新增功能、核心逻辑调整或影响范围不确定的高风险改动前，先做架构判断，并等待用户确认后再实现。

小改动、文档整理、注释调整、明确 bug 修复、轻量 UI 文案 / 颜色 / 间距调整，不需要完整架构评审；只需说明修改文件和验证方式。

需要架构判断时，先回答：

1. 是否需要新模块？
2. 是否需要新 ViewModel？
3. 是否需要新 View？
4. 是否需要 Service / Controller？
5. 是否需要 Model？
6. 是否需要持久化？
7. 会修改哪些文件？
8. 哪些文件禁止修改？
9. 本次最小可交付范围是什么？
10. 验收标准是什么？

判断标准：

- 如果功能有自己的状态、动作、生命周期、异步流程、后续扩展，必须新建 ViewModel。
- 如果 UI 有独立职责、超过 30-50 行、会复用、会反复调样式，必须新建 View。
- 如果涉及系统 API、网络、文件、数据库、播放器、权限、通知、硬件，必须新建 Service 或 Controller，不要写进 View。
- 如果功能有模型、状态、UI、服务，并且会长期扩展，必须拆成独立模块目录。

代码边界：

- 主 View 只负责组合 UI 和转发用户意图。
- ViewModel 负责状态和动作。
- Service / Controller 负责系统 API、网络、文件、数据库、播放器等底层能力。
- Model 负责数据结构。
- View 只负责展示。

MVP 实施顺序：

1. 模型
2. Service / Controller
3. ViewModel
4. 子 View
5. 接入主 UI
6. 验证
7. 文档同步

执行约束：

- 不要一次性做完整大功能。
- 不要实现用户没有明确要求的功能。
- 不要把未来计划写成已完成。
- 不要未经确认重构核心结构。
- 新增功能或高风险改动前，应先输出：架构判断、文件计划、修改范围、禁止修改范围、验收标准。

## 注释补充模板

完整注释规则以 `docs/ARCHITECTURE.md` 的“注释执行规则”为准；这里仅保留可复制的协作模板。

```text
请在不改变当前逻辑的前提下，只为有价值代码补充中文注释。

要求：
- 只解释不容易直接看懂的逻辑、平台约束、状态流和容易误改的位置
- 优先检查 SwiftUI 结构、几何 path、窗口定位、多屏判断、动画约束、预览代码
- 不要求每行都补注释；简单赋值、直观属性和自解释调用不要注释
- 对有理解成本、维护风险或平台约束的代码，按小段补充贴近实现的中文注释
- 可以删除或改写过期、重复、没有维护价值的旧注释
- 不要只写抽象概念，注释要贴近代码本身
- 注释内容使用中文，并和当前实现保持一致
```

## 注释检查模板

完整注释规则以 `docs/ARCHITECTURE.md` 的“注释执行规则”为准；这里仅保留可复制的检查模板。

```text
请检查当前文件的代码注释是否完整。

要求：
- 按“只注释有价值代码”的标准检查
- 没有注释且确实有理解成本的行或代码段要指出来
- 如果需要补注释，只补注释，不改逻辑
- 优先检查 SwiftUI 结构、Path、窗口定位、状态绑定、Preview
```
